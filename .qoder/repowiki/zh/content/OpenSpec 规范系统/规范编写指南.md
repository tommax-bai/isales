## 简介
本指南面向 OpenSpec 规范编写团队，系统阐述如何基于仓库现有的规范文件，制定统一、严谨、可维护的规范编写方法论。内容涵盖架构规范、数据模型规范、通信协议规范等各类规范的结构化编写流程，明确规范的组织原则（摘要、背景、设计决策、接口定义、约束条件等），并提供版本管理、变更追踪与文档维护的最佳实践。同时，结合仓库内真实规范示例，给出可直接参考的模板与范式，帮助团队快速产出高质量、可落地的规范文档。

## 项目结构
OpenSpec 仓库采用“规范驱动”的组织方式，核心目录结构如下：
- openspec/specs：存放各领域规范文件（architecture、data-model、service-communication、deployment-topology、device-hardware、message-contract、webhook-callback、provider-credential、ai-pipeline、call-state-machine、retry-followup、time-window、filler、human-handoff、interruption-detection、silence-activation、goal-achievement 等）
- openspec/changes：存放变更提案与归档，每个变更包含 proposal、design、tasks、specs 子目录及 .openspec.yaml 元数据
- deploy：部署与运维相关文档（README、RUNBOOK、监控配置等）

## 核心组件
OpenSpec 规范体系围绕以下核心组件展开：
- 架构规范：定义系统总体架构、仓库划分、职责边界、共享库依赖与部署模型
- 数据模型规范：定义统一的数据表清单、归属服务、跨服务一致性与 JSONB 约束
- 服务通信规范：定义服务间通信通道矩阵、队列与 Pub/Sub 边界、全局并发控制与容错策略
- 部署拓扑规范：定义 v1 单主机部署模型、环境变量契约、服务启停顺序、备份与监控
- 设备硬件规范：定义 modem-controller 进程职责、device 状态机、SIM 管理、IPC 协议与 hangup_cause 映射
- 消息契约规范：定义跨服务消息体集中定义、版本字段、通道矩阵覆盖与序列化可观测性
- Webhook 回调规范：定义触发时机、JsonLogic 表达式、Jinja2 沙盒渲染、HMAC-SHA256 签名与指数退避重试
- 提供商凭据规范：定义凭据 DB 单一事实来源、Fernet 对称加密、Admin CRUD 端点与迁移工具
- AI 管线规范：定义三层并行管线编排、JSON 输出契约、失败兜底与降级路径
- 通话状态机规范：定义状态集合、转换规则、特殊状态（WRAPPING_UP、TRANSFERRING、ACTIVATING）与 hangup_cause 单一来源
- 重试跟进规范：定义重试与跟进两个独立机制、间隔策略、上限处理与勿打识别
- 时间窗口规范：定义可通话时间窗口配置、时区策略、节假日处理与跨边界保护
- 垫词规范：定义触发场景、启动时机、选择策略、音频来源与失败兜底
- 转人工规范：定义 v1 衰减为标记 + 通知的实现与坐席工作流
- 打断检测规范：定义 SPEAKING 状态下打断判定逻辑、连续打断保护与 ASR Provider 抽象
- 沉默激活规范：定义沉默检测、激活上限、话术选择与与角色 LLM 上下文隔离
- 目标达成规范：定义实时目标达成判定、收尾行为与回调匹配

### 架构规范分析
架构规范定义了 iSales 系统的总体架构：7 仓库划分、单主机部署模型、各服务职责边界、共享库依赖关系。其关键要点包括：
- 7 仓库微服务架构与 isales-common 共享库职责
- v1 单主机部署与进程隔离
- 数据存储统一（PostgreSQL + Redis）
- 内部 HTTP 服务统一 JWT 鉴权
- 架构选型的决策记录与变更流程

## 性能考虑
- 通信通道选择：Redis Queue 用于“必须送达，可异步处理”的工作派发；Redis Pub/Sub 用于“实时、可丢失”的事件广播，避免阻塞主流程
- 全局并发控制：跨 engine 实例的全局并发使用 Redis 原子计数器（INCR/DECR），防止计数器泄漏
- 序列化与可观测性：消息序列化使用 Pydantic 的 JSON 序列化，便于日志追踪与跨服务排查
- 队列深度与重试：重试策略采用指数退避，避免雪崩效应
- 端到端延迟：垫词在 AI 管线处理期间播放，覆盖 LLM/TTS 延迟，保证对话节拍稳定

## 故障排除指南
- Redis 短暂不可用：各服务重连重试（带退避）；engine 中断重连期间不接受新拨号但可完成当前通话
- PostgreSQL 短暂不可用：各服务重连重试；正在通话中的 engine 将通话状态缓存至 Redis（v2 优化），v1 则在 DB 不可用时按异常通话处理
- modem-controller 不可用：受影响的 call_session 优雅清理（写 transcript hangup 事件）；scheduler 暂停派发直到 modem-controller 恢复
- 服务间通信故障：检查 Redis/DB/IP 通断；确认消息序列化与版本兼容；核对 WebSocket 鉴权与 fan-out 策略
- 凭据问题：确认 Fernet 主密钥正确；检查 provider_credential 表结构与加密字段一致性；使用 isales-cred-migrate 工具进行迁移与回滚

## 结论
OpenSpec 规范体系通过“规范驱动”的方式实现了跨领域的统一约束与协作，确保系统在架构、数据、通信、部署、设备、消息契约、业务流程、安全与运维等方面的一致性与可维护性。团队在编写新规范时，应遵循本文档总结的结构化编写方法与最佳实践，确保规范具备清晰性、一致性与可维护性，并通过 OpenSpec 变更流程进行版本管理与变更追踪。

## 附录

### 规范编写最佳实践
- 结构化组织：摘要、背景、设计决策、接口定义、约束条件、数据模型、流程图、序列图、状态图、依赖关系图
- 清晰性：使用简洁语言描述需求与约束，避免歧义；提供具体示例与场景
- 一致性：统一术语与命名约定；跨规范引用时保持一致
- 可维护性：将演进规则与版本控制纳入规范；提供变更追踪与回滚路径
- 可观测性：在规范中明确日志、指标与告警要求；提供调试与排障指南

- 使用 OpenSpec 变更提案（proposal）与设计（design）流程
- 通过 .openspec.yaml 元数据标识规范类型与创建时间
- 在 changes 目录下归档变更，包含 proposal、design、tasks、specs 子目录
- 通过 OpenSpec change 流程进行重大调整与决策记录
